# M4 组合导航调试实录：组合 267 m → 44.9 m 全记录

## 〇、一句话总结

**根因是 KF 时间更新的语义用错**：MATLAB `kfupdate(kf)` 时间更新会**推进状态 x**（`xk = Φ·xk`），而 P4 权威参考 `kf_predict` **只推协方差 P、从不推 x**（x 仅由量测更新驱动）。多推 x 后，未清零的慢参数态（φ/δr/db/dKod/dT）经 Φ 耦合进 δv 预测 → 反馈量 xfb 偏大 → 反馈过冲 → 组合解恶化到 267 m。

**附带修掉一个隐藏 bug**：`a2qua.m` 的 q0 项符号写反（PSINS 原版是 `cp·cr·cy − sp·sr·sy`，写成了 `+`），导致大角度下 `att→q→att` 不互逆（verify_trans 回归 20 FAIL 暴露）。

## 二、错误 1：组合解 267.1 m（不融合反而恶化）

### 现象

用户本机 MATLAB 跑 `demo_sins_dr`：

```
[SINS-only ] 水平位置 RMS = 341.8 m, 末点 = 923.7 m
[DR-only   ] 水平位置 RMS = 151.0 m, 末点 = 308.7 m
[组合(22维) ] 水平位置 RMS = 267.1 m, 末点 = 373.2 m   ← ❌ 应 ≈45.5
```

- SINS-only 341.8 vs 345.1（≈1% 差异，可接受）
- DR-only 151.0 vs 151.0（一字不差）
- **组合 267.1 vs 45.5（差 5.9 倍，融合不仅没改善还恶化了）**
- 但 dKod 估计 +0.0494（真值 +0.05）看起来又正常……

### 为什么错：一个反直觉的「假正常」

组合 267 m 的问题**不是**「KF 完全不工作」——dKod 能收敛到 +0.0494，说明滤波器在自标定。问题是**反馈过冲**：KF 每 0.1s 用 `ins.pos − dr.pos` 修正 SINS 速度，但修正量（xfb）系统性偏大，导致 SINS 速度被反复「拉过头」，位置误差反而比不融合更大。

（后面会看到：这是「KF 时间更新推了 x」导致 xfb 偏大的结果。）

### 怎么定位：三层递进，抓到第一个分歧点

定位的关键是 **「找第一个分歧点」**：MATLAB 与 Python 参考（45.5 版）逐量测对比，找到第一个不一致的量，那个量就是 bug 的藏身处。

**第 1 层：对比 z（量测新息 = SINS位置 − DR位置）与 xfb（反馈量）**

写 `diag_m4.m`（逐行复刻组合链，只在每次量测更新打印关键量）：

| 量测 | t | z 垂直 (m) | xfb 垂直 (m/s) | 结论 |
|---|---|---|---|---|
| #100 | 10s | +1.04 | +0.0002 | ✅ MATLAB 与 Python 一字不差 |
| #150 | 15s | +1.54 vs +1.55 | **+0.0008 vs +0.0006** | ⚠️ xfb 开始分道（偏大 30%） |
| #200 | 20s | +1.86 vs +1.93 | **+0.0013 vs +0.0009** | ❌ xfb 偏大 40% |
| #500 | 50s | +0.25 vs +2.21 | +0.0001 vs +0.0000 | ❌ z 垂直被「压过头」 |

→ **第一个分歧点锁定在量测 #105~#110（t≈10.5~11s）**：之前完全一致，之后 xfb 垂直分量系统性偏大。

**第 2 层：对比 K（卡尔曼增益）与 P（协方差）——排除「增益本身错」**

在 diag 里加打 `K6`（K 第 6 行 = δvU 增益）、`P66`（δvU 方差）、`P67/P69`（δvU 与位置误差互协方差）：

| 量测 | K6(3) MATLAB | K6(3) Python | P66 MATLAB | P66 Python |
|---|---|---|---|---|
| #110 | +4.066e-04 | +4.066e-04 ✅ | +1.118e-02 | +1.118e-02 ✅ |

→ **K 与 P 的关键元素全部一致**！增益本身没错。那 xfb = K·(z − H·x) 里剩下的变量只有 **x（预测态）**。

**第 3 层：对比 x_pred（量测更新前的预测态）——一锤定音**

在 diag 里加打 `x_pred(δv)`（时间更新后、量测更新前的 δv 预测值）：

| 量测 | x_pred(δvU) MATLAB | x_pred(δvU) Python |
|---|---|---|
| #110 | **+0.000058**（非零！） | **+0.000000**（恒 0！） |
| #116 | **+0.000071**（逐拍增长） | +0.000000 |

→ **找到了**！MATLAB 的预测态 δv 非零且逐拍增长，Python 恒 0。

**为什么 Python 恒 0？** 读 P4 权威源码 `gen_sins_dr.py` 第 401-404 行：

```python
# KF 预测
F = build_F(ins.qnb, ins.vn, ins.pos, ins.fn, RMh, RNh, wnin)
P = kf_predict(F, P, Q)          # ★ 只推 P！
```

而 `kf_predict` 的定义（第 307-309 行）：

```python
def kf_predict(F, P, Q):
    Fd = np.eye(N) + F*nts
    return Fd @ P @ Fd.T + Q      # ★ 只更新 P，从不更新 x！
```

**P4 的 KF 预测只推 P、不推 x**（x 只由量测更新驱动）。而 MATLAB 的 `kfupdate(kf)` 时间更新：

```matlab
kf.xk = kf.Phikk_1 * kf.xk;       % 时间更新推 x（PSINS 原版语义）
kf.Pk = kf.Phikk_1 * kf.Pk * kf.Phikk_1' + kf.Qk;
```

**多推了 x！** 这就是全部差异的来源。

### 怎么解决：A/B 实验双向证实 + 修复

**A/B 实验 A（Python 侧加推 x）**：在 Python 参考主循环加一行 `x = Fd @ x`，重跑：

```
[kffk.m 逐行翻译] 组合水平 RMS = 266.3 m   ← 与 MATLAB 267.1 一字不差！
```

→ **铁证**：推 x 就是把组合从 45.5 变 267 的唯一原因。

**A/B 实验 B（MATLAB 侧只推 P）**：把 demo 的时间更新改为对齐 P4：

```matlab
% 原来：kf = kfupdate(kf);                    % 推 x + 推 P
% 改为：只推 P（对齐 P4 kf_predict 语义）
kf.Pk = kf.Phikk_1 * kf.Pk * kf.Phikk_1' + kf.Qk;
```

重跑：

```
[组合(22维) ] 水平位置 RMS = 44.9 m   ← 对齐 P4 45.5 ✅
dKod = +0.0994（真值 +0.05）          ← 对齐 P4 +0.1004 ✅
```

→ **修复生效**！组合从 267.1 → 44.9 m，dKod 估计也从 +0.0494 → +0.0994（更接近真值 0.05 的参考值 +0.1004）。

### 为什么「推 x」会导致 267 m（机理）

1. 反馈只清零 δv（`kf.xk(4:6)=0`），**φ/δr/eb/db/dKod/dT 等慢参数态跨时间累积**（这是 dKod 能在线辨识的前提，注释里写明了）；
2. 若时间更新推 x，这些**未清零的慢参数态**经 Φ 的耦合块（`F(4:6,1:3)=Mva`、`F(4:6,7:9)=Mvp`、`F(4:6,13:15)=Cbn` 等）**灌进 δv 预测** → `x_pred(δv)` 非零；
3. 量测更新时 `xfb = x_pred(δv) + K·(z − H·x_pred)` 比「只由量测驱动」的版本**多了 x_pred(δv) 这一项**，系统性偏大；
4. 偏大的 xfb 把 SINS 速度拉过头 → 位置误差反而增大 → 下一轮 z 更大 → **正反馈恶性循环** → 267 m。

P4 的「只推 P」设计之所以工作良好：**慢参数态由量测新息缓慢驱动、不被 Φ 放大**，滤波器对位置差的响应是「温和的」，不会过冲。

## 三、错误 2：verify_trans 回归 20 FAIL（a2qua 的 q0 符号）

### 现象

修复错误 1 后跑全量回归：

```
RESULT: 105 PASS, 20 FAIL   ← verify_trans 突然 20 个 FAIL（此前 125 全 PASS）
  FAIL  2.euler2cnb↔cnb2euler 互逆 (err=1.75e+00 > 1e-09)
  ...（共 20 个，全是测试 2）
```

只有 `euler2cnb↔cnb2euler 互逆` 测试挂，其余（q2cnb↔cnb2q、qmul 合成、rv2m↔m2rv 等）全 PASS。

### 为什么错：a2qua.m 的 q0 符号写反

测试 2 的互逆链是：`att → a2qua → q → q2cnb → Cnb → cnb2q → q' → q2att → att'`。

用 MATLAB 诊断互逆链的每个环节：

```
att=[50.9852,65.7383,-60.4281] e1=8.15e-01 e2=7.01e-01   ← e1 = q2att(a2qua(att))-att 已失败
bad=20 worst=1.735e+00
q2cnb/cnb2q err=1.67e-16                                  ← 这个环节没问题
```

→ **问题出在 `a2qua` 与 `q2att` 不互逆**（环节 A），而非姿态阵环节。

查 PSINS 原版 `a2qua.m` 源码（WebSearch 核实）：

```matlab
qnb = [ cp*cr*cy - sp*sr*sy;    % q0：减号！
        sp*cr*cy - cp*sr*sy;
        cp*sr*cy + sp*cr*sy;
        cp*cr*sy + sp*sr*cy ];
```

对比我们的 `a2qua.m`（修复前）：

```matlab
q = [c(1)*c(2)*c(3) + s(1)*s(2)*s(3);   % ❌ q0 写成加号！PSINS 原版是减号
     ...
```

**q0 项符号反了**：PSINS 是 `cp·cr·cy − sp·sr·sy`，我们写成 `+`。这个二阶项在**小角度**下可忽略（demo 初始误差只有 0.5'~5'，所以 demo 一直没暴露），但 verify_trans 测试 2 用随机大姿态（±0.45π），q0 差 `2·sp·sr·sy` 就变成大误差。

### 怎么解决

`a2qua.m` q0 改为减号，并加注释标记（防手滑）：

```matlab
q = [c(1)*c(2)*c(3) - s(1)*s(2)*s(3);   % q0：减号（PSINS 原版；曾写 + 致大角度不互逆）
     ...
```

重跑：

```
RESULT: 125 PASS, 0 FAIL   ← verify_trans 恢复全 PASS ✅
```

demo 数字不变（44.9 m）——因为小角度下该项可忽略，**印证了这是个「隐藏」的约定 bug，只在极端姿态下暴露**。

## 四、调试方法论沉淀（可复用到 M5）

1. **matlab -batch 可直接跑**：本机 `D:/Program Files/MATLAB/R2023b/bin/matlab`，`matlab -batch "cmd"` 无头执行。从此验证/诊断不用等用户手动跑 + 贴输出，速度数量级提升。
2. **找第一个分歧点**：两实现逐量测对比，第一个不一致的量 = bug 藏身处。从「状态量（z/xfb）」找起，再对比「机理量（K/P）」，最后对比「预测态 x_pred」。
3. **三边 diff**：MATLAB 真实文件 vs Python 翻译 vs P4 权威源码——「自称对齐」不等于「真的对齐」，必须逐行核对语义（这次就是 `kf_predict` 只推 P vs `kfupdate` 推 x 的语义差异）。
4. **A/B 实验双向证实**：在 Python 侧加推 x → 复现 267（证「推 x 是原因」）；在 MATLAB 侧只推 P → 回 45.5（证「只推 P 是解」）。双向闭合，不靠猜。
5. **自洽测试会掩盖约定 bug**：a2qua 的 q0 符号错在小角度不可见，大姿态互逆测试才暴露——**verify 要覆盖极端输入**，不能只测「项目用得到的范围」。
